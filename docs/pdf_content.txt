1. Executive Summary 

The  platform  is  a  Solana-based  tokenized  investment  MVP  where  investors  complete  KYC/AML,  connect  a 
supported  Solana  wallet,  invest  in  approved  projects  using  USDC  or  USDT,  receive  a  project-specific  SPL  token 
representing fractional ownership, and receive profit distributions proportional to token holdings. 

The solution must be secure, compliant, auditable, and scalable. The mandatory scope requires API-based KYC/AML 
verification, multi-signature treasury custody, restricted token transfers to verified wallets only, a backend transaction 
ledger,  full  audit  trail,  client-controlled  deployment  wallets,  admin  controls,  and  future-readiness  for  a  secondary 
marketplace and other Phase 2 capabilities. 

This pack turns that scope into a concrete technical design package suitable for a proposal appendix, funding review, 
or milestone annex.

2. System Architecture Document 
2.1 Architecture Principles 

• Security-first financial architecture with strong separation between application logic, custody controls, compliance 

enforcement, and blockchain execution. 

• Modular service boundaries so the MVP can expand into a marketplace, transfer features, and additional financial 

products without redesigning the core platform. 

•  Client  ownership  and  operational  control  from  deployment  onward:  treasury  custody,  deployment  wallets,  and 

upgrade authority must not remain solely with the vendor. 

2.2 Logical Architecture 

• Presentation Layer: Next.js web application with investor dashboard and admin dashboard. 

•  Identity  &  Compliance  Layer:  registration,  authentication,  Sumsub  integration,  sanctions  /  AML  status  sync, 

wallet-to-user identity binding, RBAC, and session handling. 

•  Application  Layer:  project  catalog,  investment  workflow,  order  validation,  subscription  processing,  ledgering, 

profit distribution orchestration, admin workflows, reporting, and notifications. 

•  Blockchain  Layer:  Solana  programs,  SPL  token  minting  /  allocation,  restricted  transfers,  on-chain  profit 

distribution, and transaction verification via Solana Web3.js. 

•  Data  Layer:  PostgreSQL  for  structured  operational  data,  MongoDB  for  flexible  or  semi-structured  records, and 

immutable blockchain transaction references stored in the ledger. 

• Infrastructure Layer: AWS (or equivalent), Dockerized services, CI/CD, secrets management, logging, monitoring, 

and production security hardening. 

Logic Split Breakdown: 

Backend Responsibilities: Managing the user session, handling KYC/AML webhooks from Sumsub  

storing off-chain investment ledgers , validating investment thresholds , and calculating the mathematical 

entitlements for profit distributions off-chain. 

On-chain  Responsibilities:  SPL  token  minting,  enforcing transfer restrictions to verified wallets only holding the 
immutable   project state (supply cap, mint address), and executing the actual transfer of USDC/USDT for profit 
payouts. 

2.3 End-to-End Data Flow 

•  The user signs up and completes KYC/AML. Backend receives verification updates from Sumsub and marks the 

user as approved or restricted. 

• The user connects a supported Solana wallet. Backend links the wallet address to the verified identity record and 

updates allow-list eligibility. 

• The user selects a project, enters an investment amount, and the backend validates user status, thresholds, lock-up 

rules, and treasury routing rules. 

•  Investor  transfers  USDC/USDT  to  the  multi-signature  treasury  route;  backend  records  pending  investment  and 

verifies on-chain settlement. 

• After settlement, the system allocates the corresponding project SPL tokens to the verified wallet and updates both 

the backend ledger and on-chain references. 

•  When  profits  are  declared,  admin  submits  the  payable  amount,  backend  prepares  the  distribution  batch, Solana 

program executes proportional payouts, and all results are logged for reconciliation and investor visibility.

users is the root entity. Every investor or admin account lives here. It stores credentials, role (investor, admin), 
and account status. All other entities trace back to this table via user_id. 

sessions manages JWT and refresh token lifecycle. Tokens are stored as hashes only — never plaintext. Expiry 
and IP are tracked for security auditing. 

kyc_records  holds  one  or  more  KYC/AML  records  per  user  (a  new  record  is  created  on  re-verification).  It 
stores  the  Sumsub  applicant_id,  individual  statuses  for  KYC,  AML,  and  sanctions,  rejection reasons, and the 
raw webhook response payload as jsonb for auditability. 

user_wallets  links  Solana  wallet  addresses  to  users  via  signed-message  challenge.  A  user  can  link  multiple 
wallets. Stores the chain, link status, and the nonce used for the on-chain challenge. 

wallet_eligibility  is  the  derived  allow-list  record  —  it  joins  a  wallet  to  a  KYC  record  and  stores  explicit 
investment_allowed  and  transfer_allowed flags with validity windows. The smart contract's transfer-restriction 
program checks against this. 

projects  is  the  project  catalog.  Each  record  holds all investment parameters: supply cap, min/max thresholds, 
accepted stablecoin, the treasury wallet address, lock-up period, and subscription window. 

project_tokens is a one-to-one extension of projects storing the on-chain SPL token details: mint address, token 
name and symbol, decimals, program ID, and mint authority revocation status. 

investments  is  the  subscription  ledger.  Each  record  tracks  a  single  investor's  investment  in  a  project:  the 
amount,  stablecoin  used,  the  on-chain  settlement  transaction  hash,  and  the  resulting  token allocation amount. 
Status moves through pending → settled → allocated.

7. Custody and Authority-Control Design 

7.1 Custody Model 
•  Investor  subscription  funds  are  routed only to a multi-signature treasury wallet with no unilateral control by any 

one party. 

•  Recommended  treasury  model:  2-of-3  or  3-of-5  client-controlled  signature  set  depending  on  governance 

preference, with one or more client signers and one operational signer for execution support. 

• The backend never has direct custody of assets; it orchestrates records, validations, and monitoring only. 

7.2 Authority Matrix 
• Treasury wallet authority: client multi-signature. 

• Token mint authority: revoked after issuance window or retained under client multi-signature only. 

• Program upgrade authority: transferred to client after deployment. 

• Deployment authority: all deployments executed from client-controlled wallets. 

• Pause authorities: restricted admin role with multi-party approval policy for production. 

Admin Roles & Permissions: 

Super Admin (Client Multisig): Exclusive authority over treasury fund withdrawals , smart contract upgrades , and 

assigning/revoking mint authority. 

Operational Admin: Can create projects via /admin/projects , update public project metadata, and trigger emergency 

/admin/controls/pause-investments. Cannot move funds. 

7.3 Operational Controls 
• All treasury movement requests require explicit signing flow outside normal backend runtime. 

• All authority changes are recorded in an operational change log and linked to governance approvals. 

• Emergency actions are limited to pause functions and must not allow arbitrary withdrawal by the vendor. 

7.4 Recommended Environment Separation 
• Separate Devnet, staging, and Mainnet wallets, treasury addresses, and key material. 

• Use hardware wallets or institution-grade signer custody for production signatures. 

• Store non-custodial service secrets in a managed secrets vault with rotation policy.

8.3 Exit / Acceptance Checklist 

□ All critical user and admin flows tested successfully on target environment. 

□ Smart contract tests pass including restriction and authority scenarios. 

□ KYC / AML sync verified end to end with webhook handling. 

□ Treasury and authority configuration verified under client control.

8.4 Deployment Flow 

1.  Devnet: Contracts deployed to Solana Devnet. Backend connected to mock USDC/USDT and the 

client-provided Sumsub API (Sandbox environment). Used for internal QA, unit testing, and initial frontend 
integration. 

2.  Staging / Testnet: Contracts deployed to Solana Devnet/Testnet. Backend connected to the staging 

environment, continuing to utilize the client-provisioned Sumsub API. Used for Client Acceptance Testing 
(UAT). 

3.  Mainnet (Production MVP Launch): Final deployment of the MVP to Solana Mainnet. This phase is 

designed to accommodate execution via client-provisioned deployment wallets, establishing direct client 
ownership of the MVP infrastructure from day one if preferred
